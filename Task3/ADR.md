### <a name="_qmphm5d6rvi3"></a>**Решение**

Сценарий UC1 описывает текущий способ открытия депозита, он практически не использует возможности автоматизации, поэтому рассмотрет только сценарий UC2.

Работа с депозитами выделена в отдельный сервис для возможности дальнейшего масштабирования. Переход должен быть постепенным и безопасным, поэтому текущая реализация также сохранена, маршрутизация запросов осуществляется через API Gateway. Для уменьшения нагрузки на АБС часть данных типа справочной информации кэшируется в Deposit Db. Также для уменьшения задержек используется асинхронный обмен данными.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
- Не разбивать монолит на микросервисы, а доработать необходимые функции. Видимо, функционал приложения ограничен, поэтому для масштабирования можно запустить несколько контейнеров с этим приложением.

**Недостатки, ограничения, риски**

- Кэширование информации может привести к тому, что на момент запроса она будет не актуальной, например, ставки по депозитам.
- Необходимо провести интеграцию АБС c Kafka.
- Усложнение интернет-банка, необходимость поддержки его инфраструктуры.
